### 方針転換（2026-08-21）

**「時間帯ごとに見せる」から「時間を織り込んだ1つの答えを出す」へ。**

課題設定は「ハザードマップを見ていない人が多い。災害の種類も見る項目も多すぎて、
何を見ればいいのか分からない」。ところが旧版は操作できるものが13個あり、
**アプリ自身が同じ問題を作っていた**（時刻スライダー / 曜日3択 / 季節2択 /
ハザードレイヤ4択 / ピンON・OFF / 背景地図ON・OFF / 交通量ON・OFF / タブ3つ）。

削ったもの:

| | 理由 |
|---|---|
| 時刻スライダー・曜日3択 | 24時間ぶんのランキングを順に見るのは手間で実用的でない。全時間帯を積分して1スコアに |
| 季節2択（冬夕/夏昼） | 同じ種類のつまみ。冬の夕方に固定（消防庁自身が最悪ケースとして重視）。季節差は詳細に「事実」として残す |
| リスク地図タブ | レイヤ4択が「何を見ればいいか分からない」を再生産していた。地図は詳細シートの上部に埋め込み |
| 交通量（JARTIC） | 都心にゼロ、車の点データ。使うたびに限界の説明が必要で一元化の妨げ |
| ピン・背景地図のトグル | 常時ON。説明は設定タブへ |

**新しいスコア** — 時刻を選ばせず、全時間帯を積分する:

```
リスク時間 = Σ（全時間帯）滞在時間 × ハザード × 逃げにくさ  ／ 観測週数
```

「1週間あたり、危険度で重み付けした滞在時間」。時間軸は消えていない、内部に畳み込まれている。
サンプル（学生）での実測:

| 場所 | 週滞在 | ハザード | リスク時間 |
|---|---|---|---|
| 自宅（町屋1丁目） | 69.7h | 0.981（都内100位） | 51.67 |
| スーパー（町屋3丁目） | 1.4h | 0.991（都内47位） | 1.17 |
| バイト先（道玄坂2丁目） | 5.4h | 0.450（都内2857位） | 0.94 |
| 大学（本郷7丁目・東大構内） | 34.9h | 0.022（**都内5080位**） | 0.23 |

**長くいるから危ないのではなく、危ない場所に長くいるから危ない**が数字で出る。

### 避難場所（2026-08-21 追加）

「結局どうすればいいのか」に東京都の公式指定で答える。`src/core/evacuation.ts`。

- 東京都「震災時火災における避難場所及び避難道路等の指定（第9次・令和4年9月適用）」
- 割当区域261 / 避難場所221 / うち地区内残留地区40。gzip 78KB で同梱
- 座標 → 割当区域 → 避難場所。Python(shapely) と同じ結果をテストで固定

**⚠️ 最寄りを計算してはいけない。** 都は町丁目・町会単位で1箇所ずつ割り当てている
（避難距離3km未満、輻射熱を考慮して1人1㎡以上）。最寄りとは限らない。

**⚠️ 地区内残留地区では「逃げなくてよい」が正解。** 不燃化が進み広域避難が不要な区域で、
23区の面積の約19%。渋谷・丸の内が該当する。ここで「最寄りへ逃げろ」は誤指示。

国土地理院「指定緊急避難場所」の災害種別◎は「その場所自体が輻射熱の影響を受けない」
という意味であって「そこへ行くべき」ではない。混同しないこと。

**避難道路は使えない。** 都の指定は13本のみ（上野公園一帯などの特定系統）で、
一般的な経路網ではない。

### Googleタイムラインの取り込み（実装済み・2026-08-17）

実物のエクスポート（iPhone / Googleマップアプリ）で構造を確認して実装した。

```
トップレベルは配列。Android版は { semanticSegments: [...] } の可能性があるので両方受ける
├ visit を持つ要素        → 滞在。これだけを StayPoint にする
│    visit.topCandidate.placeLocation = "geo:緯度,経度"
│    visit.topCandidate.semanticType  = "Home" / "Work" / "Searched Address" ...
│    visit.probability = 訪問の確からしさ（**文字列**）
├ activity を持つ要素      → 移動。捨てる
│    activity.start / .end = "geo:緯度,経度"、distanceMeters、topCandidate.type
└ timelinePath を持つ要素 → 移動の軌跡。捨てる
startTime / endTime は ISO8601。**+09:00 と Z が混在する**
数値はすべて文字列で入っている。場所の名前は入っていない（placeID のみ）
```

**⚠️ タイムラインは即座には整形されない。** 2026-08-19 のエクスポート（3日分）を見たところ、
新宿区西早稲田1丁目への外出が `visit` になっておらず、**20.4kmの「in passenger vehicle」が
10.6時間**という activity 1件にまとまっていた。移動と滞在がまだ分解されていない状態。
数日経つとGoogle側で再処理される可能性がある。

`activity` の到着地を滞在として拾うことはしない。滞在時間が移動時間込みになって
曝露が歪み、中核ロジックの信頼性が落ちるため。

- 滞在判定は自前で実装していない。タイムラインが整形済みなので `visit` を写すだけ
- `semanticType` が Home / Work などのときだけ日本語名を付ける。それ以外は町丁目名で代用
- `visit.probability < 0.3` と 5分未満の滞在は捨てる。**閾値は1日分の実データしか
  見ていないので暫定**。複数日が溜まったら誤検出の落ち具合を見て調整すること
- テストは**合成データのみ**で書いている。本物の位置履歴はコミットしない（`.gitignore` 済み）

### ⚠️ 東京都外は評価できない

地域危険度は東京都のデータなので、**都外に住んでいる人は自分の履歴では何も出ない**。
実データで確認したところ、開発者本人の滞在地点が神奈川県側で判定対象外だった。

- 取り込み時に「◯件のうち◯件が東京都内でした」と明示する
- 1件も判定できなければ、理由を書いてサンプルデータへ誘導する
- 対象範囲外の場所には★を出さない（★1は「都内で最も安全」の意味になってしまうため）
- **「都外」と「市街化区域外」は言い分けていない**。町田市が南へ張り出しているため
  東京都の外接矩形に川崎市が入り、矩形では区別できないことを実データで確認した。
  正確にやるなら都境のポリゴンが要る

### 手動での場所登録（実装済み・2026-08-19）

handoff §3 の入力経路②。タイムラインが取りこぼした滞在を人手で補える。
実際、Googleが移動と滞在を分解できず外出先の滞在が丸ごと消えた例を実測している。

- 名前 ／ 位置（**地図をタップ**）／ 曜日（複数選択・平日/土日/毎日のプリセット）／ 時間帯
- 登録内容を直近4週間ぶんの `StayPoint[]` に展開する（`src/core/manual.ts`）。
  タイムラインから来た滞在と同じ形なので、以降の処理は経路を区別しない
- **住所検索は使わない。** ジオコーディングAPIに住所を投げること自体が位置情報の送信になり、
  「位置情報は端末から出ない」が崩れるため。位置は地図のタップだけで決める
- `localStorage` に保存（`src/ui/storage.ts`）。core/ に置かないのは React Native に無いため。
  移植時はここだけ AsyncStorage 等に差し替える
- 「履歴を全削除」で手動登録も消える
- 起動画面と、ランキングの空状態の両方から辿れる

`startHour === endHour` の登録は展開しない。24時間なのか一瞬なのか決まらないため
（サンプルデータで同じ形の不具合を出したことがある）。

## 設計判断（handoff から変えたところ）

### 1. ハザードAPIを置かない

統合後のデータが gzip 0.84MB なので全部クライアントに同梱した。
handoff §9 は「町丁目コードのみサーバーに送信」だったが、**送信そのものを無くした**。
Cloudflare は静的配信だけ。

### 2. ランキングの並び順を個人リスク順にした

handoff 内に矛盾があった:

- §6-2 … `重要度 = 行動スコア × リスクスコア`（時間の項がない）
- §8 … 「スライダーを動かす → ランキングの順位も入れ替わる」「デモで最も効く挙動」

§4 のリスクモデル（ハザード×曝露×脆弱性）自体が時間依存なので、**個人リスク順**を採用。
時刻を動かすと1位が実際に入れ替わる:

```
平日13時 → 1位 大学
平日21時 → 1位 バイト先（渋谷）
平日 3時 → 自宅以外は全て曝露0。生活圏としての重要度順にフォールバック
```

`重要度`（行動×リスク、時間非依存）は同点時のタイブレークとして残してある。

### 3. ★の出自

- 行動側 = あなたの中での相対値（自分の場所の最大値で正規化）
- リスク側 = 都内5,192町丁目の中での相対値（**順位から引き直す。5段階ランクは流用しない**）

詳細シートでは見出しで区切っている。

## 精査で見つけて直した不具合（2026-08-17）

| | 症状 | 原因 |
|---|---|---|
| サンプルデータ | 新宿駅の「乗換」が平均**1,444分**（24時間）滞在になっていた | `startHour === endHour` を `24 - 8 + 8 = 24時間` と解釈していた。`minutes` を明示できるようにし、同値の場合は例外を投げるようにした。回帰テスト2件追加 |
| 地図 | スタイル読み込み前のレイヤ切替・背景地図ON/OFFが黙って捨てられ、ボタンと地図がずれる | `isStyleLoaded()` が false のとき `return` していた。`load` イベントで `styleReady` を立て、依存に入れて再適用する |
| 曝露 | 分母（観測日数）が場所の走査順に依存していた | その日の重みを「最初に見つかった滞在」から取っていた。日付の00:00から計算するよう修正 |
| 祝日タブ | 選ぶと**全ての場所が0%**になる | 祝日の暦が無く観測日数が常に0で、分母が0だった。土日の履歴で代用し、代用したことを画面に明示 |
| 詳細シート | Escapeで閉じられない | keydownハンドラを追加 |
| データ読込 | 失敗したPromiseを永久にキャッシュし、リトライしても同じエラーを返す | 失敗時にキャッシュを捨てる |
| 実装の重複 | 百分位の計算が詳細シートに手書きで再実装されていた／曜日区分の分岐が地図と`traffic.ts`に二重にあった | `dangerPercentile` と `seriesForDayType` に寄せた |
| ドキュメント | gzipサイズが 0.75MB のまま（実際は0.84MB）、propertiesの一覧に順位カラムが無い | 実測値に更新 |
| 取り込み | ハザードデータの読み込み完了前にインポートすると、`index` が null で判定が全て外れ、**「判定できる滞在はありませんでした」と誤案内したうえ取り込んだデータを捨てる** | 未着なら先に弾き、「読み込み中です」と案内する |
| 配信 | `.geojson` は `application/geo+json` になり、CDNの圧縮対象MIMEタイプに入らない可能性があった（4.65MBが無圧縮で配信される恐れ） | `.json` に変更。本番で `Content-Encoding: br` を確認 |
| 重複 | `5192` が `explain.ts` 3箇所と `MapTab.tsx` にハードコードされ、`TOTAL_CHOCHOME` が使われていなかった | `TOTAL_CHOCHOME` に集約 |

## 既知の割り切り

- **タブを切り替えると地図の状態が失われる**。`{tab === 'map' && <MapTab/>}` で
  アンマウントされるため、ズーム位置・選択中のレイヤ・ピンの表示切替が初期値に戻り、
  地図も作り直しになる。時刻だけはグローバル状態なので保持される。
  デモの導線が「ランキング → 地図」の一方向なので今回は直していない。
  直すなら `layer` と カメラ位置を App に持ち上げる
- **場所のIDが位置依存**（`place-${i}`）。いま除外設定はリセット時に必ずクリアされるので
  実害は無いが、データを差し替えても除外が残る作りにすると別の場所を除外してしまう

## 見た目の作り直し（2026-08-19）

「全体的に安っぽい」という指摘を受けて、原因を8つ特定して直した。

| 原因 | 対応 |
|---|---|
| 絵文字ロゴ `🐿` が仮置きに見える | `src/ui/Mark.tsx` にSVGの栗鼠マークを起こした。小さくても分かるよう巻いた尻尾を主役にしている。色は `currentColor` |
| ★がテキスト文字でフォント依存・不揃い | `Stars.tsx` をSVGに。`.stars__on` / `.stars__off` で塗り分ける |
| **全要素に1pxの枠** → ワイヤーフレームに見える | 枠を外し、**面の明度差＋ごく弱い影**で階層を作る（`--shadow-1/2/3`） |
| 面の差が浅く（`#faf7f4` と `#ffffff`）カードが浮かない | 背景を `#f4efe9` に沈めた。ダークは影が効かないので影を `none` にし、面の差だけで階層を作る |
| 文字サイズが11〜19でバラバラ | `--fs-xs/sm/base/md/lg/xl` のスケールに統一。時刻表示は17→21pxにして主役にした |
| 余白が5/6/7/10/12/14px混在 | `--sp-1..6`（4/8/12/16/24/32）に統一 |
| 日本語の行間・字間が未調整 | `line-height: 1.75` / `letter-spacing: 0.02em` を既定に |
| ネイティブのスライダーとセレクト | 自前で描画（つまみ22px、トラック6px、セレクトの矢印もCSSで） |

あわせてボトムシートにつまみを付け、背景をぼかし、タブの選択に下線アニメーションを入れた。

| 面の上の文字 | **9.80** |
| 文字色 on 白 | **4.99** |
| 文字色 on 淡色面 | **4.57** |
| 文字色 on 暗背景（ダーク） | **12.55** |

いずれも本文基準の4.5以上。土色 `#b4621f` → 黄緑 `#9acd32` → 若葉 `#91e041` と変えている。

**アクセントを文字色に使わないこと。** 使うなら `--accent-text`。
`MapTab` の「ここはあなたが週n回訪れています」で一度やらかしている。

**ピンの輪郭は `--accent` から切り離してある。** アクセントが黄緑なので、
緑〜黄緑のハザード領域（ランク1・2）の上でピンが見えなくなるため。
`--pin` はハザード全色から距離120離れた濃い茶。
（変更前の土色 `#b4621f` は距離33しかなく、もともと弱かった）

**ハザードとの色被りは許容する判断**（2026-08-19）。テーマの若葉色 `#91e041` は
ハザードのランク2 `#b0b04e` と近い。面の役割が違う（UI部品 vs 地図の塗り）ため実用上は
区別できるが、地図上にアクセント色の要素を増やすときは注意すること。

### ハザードの塗り = 緑→赤のまま（2026-08-19 判断）

直感的で一目で分かることを優先した判断。

ただし実測した問題が2つ残っている。質疑で色覚配慮を聞かれたら、把握した上での判断だと
答えられるようにしておくこと。

| | 明度が単調に暗くなるか | 隣接色の最小差（通常 / 2型 / 1型） |
|---|---|---|
| **現行（緑→赤）** | **いいえ**（0.292→0.408→0.382→0.233→0.124） | 49.2 / **22.0** / **23.7** |
| 案A 土色の濃淡（不採用） | はい | 65.9 / 64.8 / 63.7 |

1. **ランク2と3が2型色覚でほぼ区別できない**（色差 49.2 → 22.0）。日本人男性の約5%が該当
2. **明度が単調でない。** ランク1→2 で一度明るくなるため、最も安全なランク1(0.292)と
   危険なランク4(0.233)が近い明度になり、白黒印刷や弱視の環境で崩れる

緩和されている点: 地図をタップすれば順位・危険量が数値で出るので、**色だけが情報の経路ではない**。
詳細シートも★と都内順位を併記している。

やるなら緑→赤のまま明度を単調にする調整で1と2の大半は消せる（見た目の系統は変わらない）。
